# 换基座：Qwen3-30B-A3B（MoE）上的同一套配方

> 2026-09-18。把 8B 那套 LoRA 配方原样搬到 `Qwen/Qwen3-30B-A3B`（MoE，总参 30.5B /
> 激活 3.3B），评测口径、脚本、硬件（昇腾 910C）、采样参数全部与
> `results/standard_eval.md` 相同，全量 26,368 题，逐题配对检验。

## 先说结论

1. **HKMMLU 0.6467，超过原第一名 5.69pp**（95% CI [+5.07, +6.38]，p = 2.5e-63）。
2. **这不是基座白送的。** 裸基座在同一口径下只有 **0.4487**；即便给足它最受益的
   格式帮助（0.5252），仍低于原第一名的 0.5897。
3. **但也不是配方的功劳。** 同为仅注意力 LoRA，30B 对 8B 是 **+10.50pp**；
   而在 8B 上「七模块 vs 仅注意力」只有 **+0.22pp（p=0.417，不显著）**。
   **基座容量主导，LoRA 挂哪几个模块量不出差别。**
4. **30B 不是全面更好。** 「普→粤」——本组唯一直接度量「能不能产出粤语」的指标
   ——反而最差（44.51，8B 是 52.36）；而「粤→普」是本组最高（57.30）。
   **更大的基座把粤语「听懂」做得更好，把粤语「说出来」做得更差。**
5. 因此**不设旗舰**：知识问答与格式遵从用 30B，生成地道书面粤语仍用 8B。

## 配方与训练

与 8B 版本的唯一有意差异是 `target_modules`：

| | 8B（发布版） | 8B（对照臂） | 30B-A3B |
|---|---|---|---|
| 基座 | `Qwen/Qwen3-8B` | 同左 | `Qwen/Qwen3-30B-A3B` |
| 挂载模块 | q,k,v,o,gate,up,down（7 个） | q,k,v,o（仅注意力） | q,k,v,o（仅注意力） |
| 可训练参数 | 87.3M / 8.28B = 1.055% | 31.5M / 8.21B = 0.384% | **26.7M / 30.56B = 0.087%** |
| r / alpha | 32 / 64 | 32 / 64 | 32 / 64 |
| 其余超参 | lr 1e-4，2 epochs，max_len 1024，warmup 3%，seed 42 | 同左 | 同左 |
| 用时 | 1 小时 1 分（4×H100） | — | **3 小时 0 分（8×H100）** |
| best eval_loss | **1.2059** @ step 8400 | 1.2615 @ step 8526 | 1.2441 @ step 8400 |

**为什么 30B 只能挂注意力。** MoE 的 `gate_proj/up_proj/down_proj` 是**每个专家一份**：
48 层 × 128 专家 × 3 = **18,432** 个专家线性层。把它们放进 `target_modules`，
LoRA 挂载点数量会失控（显存与 adapter 体积都不可控）。所以限定为注意力四投影，
48 × 4 = **192** 个模块。

这不是随意让步——8B 上专门跑了一条**仅注意力对照臂**来量这个让步的代价，
结果是 **+0.22pp、p=0.417，量不出差别**（详见 `results/standard_eval.md`）。
**所以 30B 这一轮的结果可以干净地归给基座，而不是归给被迫简化的配方。**

### eval_loss 又一次没有预测任务表现

三臂的 eval_loss 排序与 HKMMLU 准确率排序**不一致**：

| | eval_loss | HKMMLU |
|---|---|---|
| 8B 七模块 | **1.2059**（最低） | 0.5394 |
| 30B-A3B 仅注意力 | 1.2441 | **0.6467**（最高） |
| 8B 仅注意力 | 1.2615（最高） | 0.5416 |

**eval_loss 把最好的那个排在中间。** 8B 两臂之间 eval_loss 差 0.056（看着像 7 模块明显更好），
任务指标却是 +0.22pp 且不显著、方向还相反。**不要用 eval_loss 预告排名。**

### MoE 的吞吐不能用随机权重试跑来估

起跑前用 `from_config` 造随机权重做过显存试跑，量到 **0.78 s/step**，据此报「1.85 小时」。
真权重实测 **1.20 s/step → 3.01 小时**，低估 **54%**。

原因：MoE 的路由依赖权重**数值**。随机权重下门控输出接近均匀、token 在 128 个专家间平摊；
真权重下路由有强偏好，专家负载不均，每一步都要等最慢那个专家。

**随机权重试跑能测准的只有显存占用和挂载点数量**（实测 `trainable=26.7M / 30.56B = 0.087%`
与真跑一字不差），**吞吐只是下界**。dense 模型没有这个问题，这是 MoE 专有的。

## 合并与体检

`merge_lora.py` 单进程合并，产出 `merge_check.json`：

```
n_compared     = 18867
n_changed      = 192          （= 48 层 × 4 个注意力投影，一个不多）
max_rel_delta  = 0.15516
```

18,867 这个数可以手算核对：48 × (128×3 + 4 注意力 + 1 门控 + 2 层范数 + 2 个 q/k_norm)
+ embed + lm_head + 末层范数 = 18,867。**对得上，说明没有张量被漏掉或被融合。**

`max ‖ΔW‖/‖W‖ = 0.1552` 略高于脚本里写的「r=32/alpha=64 正常应在 0.01–0.10」这个带。
合理解释是 30B-A3B 的 `hidden_size` 只有 2048（8B 是 4096），注意力矩阵本身更小，
同样秩 32 的更新除以更小的 ‖W‖ 就更大。距 v1 发散时的 0.50–1.06 仍远，
梯度也一路收敛（grad_norm 2.285 → 0.5235）。

**这一轮合并做了两次**，在两台不同集群、两个不同 `transformers` 大版本（5.6.2 与 4.57.1）
之下，三项数值完全一致。这一条是有必要的：不同版本可能把 128 个专家存成融合的 3D 张量，
那样 `n_compared` 会立刻塌掉——**用对账而不是用信任来确认「是同一个操作」**。

## 二、把「格式分量」从增益里扣掉

主表口径（strict：末尾只给「答案：」）对**未经指令微调的基座天然不利**。
本项目此前已量到：格式脚手架对 8B 基座有 **+5.51pp** 的增益，是 8 个模型里最大的
（见 `results/prompt_ablation.md`）。所以直接用 strict 口径的差距去说「微调贡献了多少」，
会把「学会按格式作答」算进「知识变多了」。

因此把本模型与其基座在 **scaffold 口径**（末尾附一句「請喺最後一行寫『答案：X』」）
下全量重测一次：

| | strict | scaffold | 口径带来的增益 |
|---|---|---|---|
| `Qwen/Qwen3-30B-A3B`（基座） | 0.4487 | 0.5252 | **+7.65pp** [+7.02, +8.28] |
| 本项目 30B | 0.6467 | 0.6660 | +1.93pp [+1.50, +2.36] |
| **同口径差距** | **+19.79pp** | **+14.07pp** [+13.43, +14.72] | — |

算式自洽：19.79 − 7.65 + 1.93 = 14.07。

**读法：**

- 同口径、且选的是**对基座最有利**的那一档，微调仍带来 **+14.07pp**。
- 基座即便拿到格式帮助（0.5252），**仍低于原第一名的 0.5897**。
  所以「超过第一名」这件事是微调挣来的，不是基座本来就有的。
- strict 与 scaffold 的差 5.72pp，是两者**格式收益之差**，应当计入
  「微调教会了格式遵从」这一项，而不是知识。

> ⚠️ 主表一律用 strict 口径。scaffold 一列只用于本节的分量拆解，**不进排名**。
> 理由见 `results/prompt_ablation.md`：脚手架偏向最需要它的模型，
> 「每个模型取自己最优口径」在有不对称助力时不是中立口径。

### 一个被推翻的预测

开跑前的预期是：解析失败率已近零的模型从脚手架拿不到增益，甚至为负
（`results/prompt_ablation.md` 里 0 解析失败的两个对手是 −0.14pp 和 −0.93pp）。

**本模型拿到 +1.93pp，p = 1.05e-18，不是噪声。** 而且平均输出**没有变长**
（5.4 → 5.8 token），说明它并没有因为那句话而改去「先写推理再作答」。

结论要改成：**那句格式提示不只是让解析跑通，它还改变了选项的选择本身。**
「最不需要它的模型获益最少」仍然成立（本模型 +1.93pp < 8B 发布版 +3.00pp
< 8B 基座 +5.51pp），但「不获益」不成立。

## 五、一个解释，以及它还缺什么

「听懂更好、说出来更差」这个反差，与**干预比例**这个说法一致：

| | LoRA 改动的张量 | 占全模型 |
|---|---|---|
| 8B dense（仅注意力） | 192 | 192 / 291 ≈ 66% |
| **30B-A3B MoE（仅注意力）** | **192** | **192 / 18,867 ≈ 1%** |

同样 192 个模块，在 8B 稠密模型里覆盖了大部分权重矩阵，在这个 MoE 上只有百分之一。
风格/语域这类分布层面的改变可能主要需要动 FFN，而 MoE 的 FFN 全在专家里、一个没动；
与此同时基座本身更强的粤语理解力透了出来。

**但这只是一个与数据相符的解释，不是结论。** 要证成它，至少还需要：

1. 在 30B 上做一条**含部分专家层**的 LoRA 臂（例如只挂共享门控，或按路由频次挑
   top-k 专家），看「普→粤」是否回升；
2. 在 8B 上反向做一条**更稀疏**的臂（例如只挂 q/v，r=8），看「普→粤」是否下降。

这两条本轮都**没有做**。在做出来之前，第 4 条结论应当只当作现象陈述。

## 六、口径可比性：我们这套 harness 和 HKMMLU 论文对得上吗

本页所有数字来自我们自己实现的 harness。要把 0.6467 和
[HKMMLU 论文](https://arxiv.org/abs/2505.02177) Table 1 那张表并列，
必须先证明两套打分口径一致——**两张表之间原本没有任何共享模型**，
而「跨口径数字当可比数字用」正是本项目已经栽过的错误。

做法：把论文 Table 1 里的三个 `Qwen2.5-Instruct` 放进**我们这套 harness**
（官方 strict、全量 26,368、解析失败按答错），和论文靶值逐个对账。
用三个尺寸而不是一个：一个点只能给偏移，三个点才能看偏移是不是常数。

| 模型 | 我们实测 | 论文 Table 1 | 偏移 | 我们这边的解析失败率 |
|---|---|---|---|---|
| `Qwen2.5-3B-Instruct` | 49.32 | 50.3 | **−0.98** | 0.0000 |
| `Qwen2.5-7B-Instruct` | 56.61 | 57.2 | **−0.59** | 0.0006 |
| `Qwen2.5-14B-Instruct` | 62.82 | 62.3 | **+0.52** | 0.0067 |

**偏移跨度 1.50pp，均值 −0.35pp，而且没有系统方向（两低一高）。**
按事先设好的判据（跨度 ≤3pp 即认定为口径一致），**两套 harness 一致，
本页的数可以直接与论文表并列。** 折算到论文刻度，本项目 30B 约为 **65.0**。

### 一个被这组数据推翻的推断

在跑这个桥之前，观察到「我们量裸 `Qwen3-30B-A3B` 只有 0.4487，而论文给
`Qwen2.5-14B` 是 0.623」，当时的推断是**我们的 harness 明显更严**（怀疑是
「解析失败算答错」而论文没有）。**这个推断是错的。**

三个 instruct 模型在我们这里的解析失败率是 0.00%／0.06%／0.67%，
分数也与论文一致——harness 并不苛刻。真因是**未经指令微调的基座本身就不按格式作答**
（`Qwen3-30B-A3B` 平均输出 495 token，答完不停），这是模型属性，不是打分口径问题。

附带的 scaffold 臂也印证这一点：instruct 模型从格式脚手架只拿到很小的增益
（7B +0.70pp、14B +1.47pp），远小于基座的 +7.65pp。

**结论：不是 SOTA。** 上面 5 个全部是 70B 以上或闭源前沿模型，
与第一名 DeepSeek-V3 差 **10.1pp**。

**能说的是：在论文表里所有 ≤34B 的模型中排第一**（下一位 `Qwen2.5-14B` 62.3），
而本模型每 token 只激活 3.3B 参数。

复现：`results/bridge/` 下五个 json；作业脚本 `code/npu_bridge.sbatch`（未随仓库发布）。
