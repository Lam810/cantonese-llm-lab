# 复盘：一个粤语 LoRA 微调为什么会训坏，以及怎么在上传前就发现

> 对象：`Qwen3-0.6B` + LoRA(r=8) 的粤语问答微调（2025 年训，2026-09 才做评测）。
> 结论先说：**模型是坏的**——30 条粤语提问里 93.3% 的回答是重复乱码。
> 根因是**训练发散**，不是合并出错；而当时之所以没发现，是因为**整个训练没有验证集**。

## 1. 症状

贪心解码，30 条日常粤语提问：

```
Q: 香港有咩好玩嘅地方？
A: 香港有咢好玩嘅地方，如咢咢咢咢咢咢咢咢咢咢咢……

Q: 點樣由旺角去中環最快？
A: 由旺角去中環，由旺角去中環，由旺昂去中昂，由昂昂去昂昂，由昂昂去昂昂……

Q: 你可唔可以解釋下咩係強積金？
A: 说明说明说明说明说明说明说明说明说明……
```

退化率（回答里存在 6 字以上片段重复 3 次及以上）**93.3%**；同一套提问下，未微调的基座是 **0%**。

## 2. 训练日志为什么没报警

`trainer_state.json` 看起来非常正常：

| step | loss |
|---|---|
| 100 | 1.5907 |
| 200 | 0.2516 |
| 6400 | 0.2270 |
| 6600 | 0.2149 |

**200 步内 loss 从 1.59 掉到 0.25，之后 6400 步几乎不动。** 当时的读法是"收敛了"。
实际上这是塌进了一个退化解——模型学会了输出低熵的重复串，训练 loss 自然低且平。

关键在于 `training_args.bin` 里：

```
eval_strategy = "no"
```

**没有验证集、没有 eval_loss、没有早停、`best_metric: None`。** 在只有训练 loss 的情况下，
"loss 低且平"和"训练发散成退化解"这两件事**长得一模一样**。第一次 eval 就能把它们分开。

## 3. 定位：是训练发散，不是合并出错

仓库里同时有合并后的完整权重和未合并的 LoRA adapter，所以可以做三路对照。

### 3.1 逐模块权重差 ‖ΔW‖/‖W‖

把合并权重和原始基座逐张量比：310 个张量里 **254 个完全相同**，只有 `q_proj`/`v_proj` 变了
——和 LoRA 的 target_modules 完全吻合，说明合并本身"挂对了地方"。但变了的那 56 个：

```
q_proj 逐层:  0–22 层   0.046 ~ 0.154
             23 层     0.496
             24 层     1.044      ← 更新量比原权重矩阵本身还大
             25 层     0.815
             26 层     0.670
             27 层     1.058
v_proj 逐层:  全 28 层  0.057 ~ 0.171
```

r=8 / alpha=16 的 LoRA，合并后的相对差正常应在 **0.01–0.05** 量级。
**最后 5 层的 `q_proj` 到了 ~1.0，等于把这几层重写了一遍。** 而 `v_proj` 全程正常——
发散是**结构化的**：只打在最靠近输出的几层的 query 投影上。

### 3.2 把未合并的 adapter 挂回原始基座

如果只是合并环节出错（例如在 4bit 量化基座上训、却合并回全精度基座），
那么"基座 + adapter"应当是正常的。实测：

```
base            → 输出连贯，有完整思考段
base + adapter  → QAQAQAQAQA… / 由昂昂昂昂昂… （同样退化，但退化形态不同）
merged          → 咢咢咢咢… / 说明说明说明…
```

**两者都坏 ⇒ 合并不是根因，训练阶段就已经发散。**
（附带一个坑：老版本 `peft` 读不了新版 `adapter_config.json`，会报
`LoraConfig.__init__() got an unexpected keyword argument 'corda_config'`，
要装新版 peft 才能做这个对照。）

### 3.3 嫌疑最大的超参组合

```
learning_rate       = 2e-4
lr_scheduler_type   = linear
warmup_steps        = 0        ← 无 warmup
fp16 = False, bf16  = False    ← 全程 fp32
num_train_epochs    = 3
effective batch     = 16  (per_device 4 × grad_accum 4)
LoRA: r=8, alpha=16, target = q_proj, v_proj
```

2e-4 对 r=8 的小 LoRA 不算离谱，但**零 warmup + 线性衰减 + 小 batch**，
前几十步的更新会很猛；配合"只挂 q/v、rank 很低"，全部压力集中在少数几个矩阵上。
发散集中在最后几层的 `q_proj` 与这个解释一致。

## 4. 评测：微调到底带来了什么

| | HKMMLU 总体 | HK 子集 | HKDSE 子集 | 退化率 | 中位回答长度 |
|---|---|---|---|---|---|
| 微调模型 | 31.48% | 39.39% | 26.22% | **93.3%** | 129 |
| 原始基座 | 31.06% | 38.17% | 27.56% | 0.0% | 224 |
| 随机基线 | 25.00% | 25.00% | 25.00% | — | — |

n = 3300 题（每个 config 取 50 题，共 66 个 config），标准误约 0.8pp。
**31.48% vs 31.06% 的差距等于零**——微调没有带来任何知识增益，这对只喂问答数据的
LoRA 是预期之内的。真正的问题是它把生成能力弄坏了。

## 5. 三条可以直接抄走的教训

**① 没有验证集的 SFT，训练 loss 曲线不能证明任何事。**
"loss 掉得快然后走平"既可能是收敛，也可能是塌进退化解，只看训练 loss 区分不了。
`eval_strategy="steps"` + 早停 + `load_best_model_at_end` 是最低配置，不是可选项。

**② 上传前跑一次贪心解码的退化检测，成本几分钟。**
30 条提问、`max_new_tokens=128`、正则 `(.{6,})\1{2,}` 数一下重复片段，就能拦住这次事故。
指标本身很粗糙，但它抓的是"模型还会不会说人话"这种一票否决的问题。

**③ 权重差 ‖ΔW‖/‖W‖ 是最快的 LoRA 体检。**
一行范数比值就能同时回答三个问题：改了哪些层（对不对得上 target_modules）、
改动量是否在量级上合理、发散是否有结构。比翻训练日志快得多。

**④ 顺带一条自己踩的：跨简繁的字符串指标必须两种字形都写。**
我最初的"普通话标记词"只写了简体（`他们`/`什么`/`这么`），而语料经 opencc 转繁后
变成 `他們`/`什麼`/`這麼`，**整张表静默失配**，把"粤语纯度"虚高成 0.964；
补上繁体形后是 0.824。简繁混排的语料上做任何词表匹配，都要先想这一层。
